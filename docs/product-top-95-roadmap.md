# Roadmap «Мастерок 9,5»

## Цель

Довести каждый ключевой слой getmasterok.ru до уровня не ниже 9,5 из 10 и
удерживать этот уровень после новых релизов. Цель относится к качеству продукта,
а не к субъективной визуальной оценке одного экрана.

Работа считается завершённой только по доказательствам четырёх типов:

1. код и детерминированные тесты;
2. реальные сценарии в production-сборке на desktop и mobile;
3. измерения реальных пользователей без local/preview-трафика;
4. для поиска и продуктовой понятности — наблюдение после достаточного лага.

Позиции в поиске, трафик и конверсия зависят не только от кода, поэтому их нельзя
гарантировать релизом. Для SEO/AEO 9,5 означает сначала технически и содержательно
сильную систему, затем подтверждение результата данными за сопоставимые периоды.

## Как считается 9,5

Каждое направление получает собственный scorecard из 20 проверок по 0,5 балла.
Порог 9,5 достигнут, когда:

- выполнено не менее 19 проверок из 20;
- нет открытых дефектов P0 и P1;
- нет неподтверждённых формул, ложных обещаний и «правдоподобных» результатов из
  невалидного ввода;
- обязательные автоматические и браузерные ворота зелёные;
- единственный допустимый незакрытый пункт — P2 с известным влиянием и сроком.

Одна и та же проверка не засчитывается дважды. Lighthouse не заменяет полевые
Core Web Vitals, unit-тест не заменяет пользовательский сценарий, а валидный
JSON-LD не доказывает поисковый эффект.

## Приоритеты и критичность

- **P0:** неправильный расчёт, опасный совет, потеря результата, утечка данных,
  production недоступен.
- **P1:** сломанный основной сценарий, web/mobile divergence, невалидный ввод даёт
  правдоподобный результат, существенная недоступность или измерительная ошибка.
- **P2:** заметная фрикция, непонятный текст, визуальная непоследовательность,
  пропущенное объяснение без ошибки итогового расчёта.
- **P3:** косметика, которая не влияет на успешность, доверие и измерения.

Пока существует P0/P1, косметические улучшения не повышают итоговый балл выше 9,0.

## Программа работ

### Phase 0. Честная база измерений

Цель: перестать принимать решения по загрязнённым или несопоставимым данным.

- [x] Добавить allowlist production-доменов для загрузки Метрики/GA4, SPA-хитов,
  продуктовых событий и Web Vitals.
- [x] Подтвердить в production-сборке: с localhost нет запросов к `mc.yandex.ru`,
  `googletagmanager.com` и `google-analytics.com`; HTML с production Host содержит
  оба счётчика.
- [ ] После выпуска проверить на публичном домене реальные pageview, событие и
  Web Vitals без дублей.
- [x] Зафиксировать словарь событий, владельца, параметры, PII-ограничения и
  правило дедупликации.
- [ ] Собрать baseline за 14 полных дней: старт, валидный результат, ошибка,
  экспорт, сохранение, переход в связанный инструмент, device и шаблон страницы.
- [ ] Создать scorecard-dashboard и пороги регрессии без смешивания GA4, Метрики,
  Вебмастера и GSC в одну метрику.

Ворота выхода: production-данные чистые, каждое число имеет источник, период и
определение; неизвестное явно отмечено как неизвестное.

### Phase 1. Расчётное ядро и паритет

Цель: закрыть риск «красиво, но считает неправильно» до унификации интерфейса.

1. Разделить каталог по риску: конструктив/электрика/отопление, большие закупки,
   отделка, справочные расчёты.
2. Для каждого калькулятора составить контракт:
   `ввод → чистая математика → field-факторы → запас → упаковка → результат`.
3. Проверить MIN/REC/MAX, единицы, дефолты, ноль, границы и большие значения.
4. Убрать silent clamp и stale result во всех формах.
5. Синхронизировать canonical → web → Flutter и закрыть parity на 100%.
6. Для высокорисковых формул приложить источник или явно помеченное допущение.

Phase 1.0 закрывает пункт 1 машинно проверяемым реестром:
`docs/calculator-risk-register.md`. Он покрывает 65/65 опубликованных
калькуляторов и отделяет наличие canonical/engine/parity/tests от ещё не
выполненного независимого предметного ревью.

Ворота выхода: `npm test`, `npm run test:parity`, Flutter parity и независимый
аудит критичных формул зелёные; P0/P1 расчётов равны нулю.

### Phase 2. Единый лучший сценарий калькулятора

Цель: одна предсказуемая модель работы для всех калькуляторов.

1. Утвердить общий контракт поля, подсказки, ошибки, единицы и точности.
2. Утвердить общий контракт ResultBlock: точная потребность, к покупке, остаток,
   запас, допущения, факторы, сценарии и практический следующий шаг.
3. Привести к нему репрезентативные шаблоны, затем тиражировать по каталогу.
4. Проверить пустое, валидное, невалидное, длинное и восстановленное состояние.
5. Проверить desktop 1440×900 и mobile 390×844 в реальном браузере.
6. Провести benchmark на типовых задачах и исправить причины ошибок пользователей.

Ворота выхода: 95% успешных benchmark-задач без подсказки, нет silent clamp,
stale result и нерасшифрованных покупных итогов.

### Phase 3. Визуальные инструменты

Цель: числовой расчёт и визуальная схема дают одну правду.

1. Эталонные геометрические кейсы для плитки, ламината, кирпича и доски.
2. Масштаб, ориентация, шов, смещение, подрезка, openings и запас.
3. Связь с калькулятором без повторного ввода и потери режима.
4. Экспорт PNG/PDF/share, пригодный к передаче мастеру.
5. Touch, zoom, landscape, переполнение и доступные альтернативы canvas/SVG.

Ворота выхода: эталонные кейсы совпадают с числовыми результатами, а полный
сценарий проходит на desktop/mobile без скрытых ограничений.

### Phase 4. Главная, поиск и информационная архитектура

Цель: новый пользователь быстро понимает продукт и находит нужный расчёт.

1. Сформулировать один главный value proposition без маркетингового шума.
2. Проверить порядок первого экрана: задача → поиск/категория → доверие → пример.
3. Развести «калькуляторы», «визуальные инструменты», «проекты» и «Михалыча».
4. Улучшить поиск: опечатки, синонимы, нулевой результат, недавние задачи.
5. Убрать конкурирующие CTA и декоративные блоки без продуктовой функции.
6. Проверить five-second test и поиск пяти популярных задач на mobile/desktop.

Ворота выхода: не менее 90% участников правильно объясняют ценность после пяти
секунд; не менее 95% находят целевой инструмент максимум за два действия.

### Phase 5. Доступность, скорость и устойчивость

Цель: убрать технические ограничения, которые не видны на одном скриншоте.

1. Автоматический axe/Lighthouse-проход по главным шаблонам.
2. Ручная клавиатура, screen reader smoke, 200% zoom, contrast и reduced motion.
3. Performance budgets в CI и контроль third-party кода.
4. Полевой RUM по шаблону, устройству и версии релиза.
5. Smoke отказов Ghost/API/RSC, error boundary и наблюдаемость 404/500.
6. Регрессионная матрица Chrome/Firefox/WebKit и Android-класса устройств.

Ворота выхода: WCAG 2.2 AA, целевые Core Web Vitals p75 и error-free sessions
≥ 99,5% подтверждены не только лабораторно.

### Phase 6. Доверие, SEO, AEO и содержательная глубина

Цель: сделать результаты цитируемыми и проверяемыми, не создавая thin content.

1. Источник, дата проверки, авторство/рецензирование и границы применимости.
2. Согласовать видимый HTML с FAQ/HowTo/Calculator JSON-LD и DOM-якорями.
3. Проверить canonical, sitemap, robots, redirects и индексируемые варианты URL.
4. Строить новые кластеры только из запросных данных и незакрытого интента.
5. Усилить внутренние связи `расчёт → раскладка → инструкция → сохранение`.
6. Через 6–8 недель сравнить запрос → URL → показы → клики → CTR → позиция.

Ворота выхода: технический и редакционный scorecard 9,5; рост или нейтральность
защитных метрик подтверждены после лага. Недостаток данных не подменяется оценкой.

### Phase 7. Финальная валидация уровня 9,5

1. Повторный аудит всех 12 scorecard независимым проходом.
2. 20–30 сценариев: новичок, прораб, mobile, слабое устройство, клавиатура.
3. Проверка production, а не только preview или локальной сборки.
4. Две недели без P1-регрессии и один полный цикл продуктовых данных.
5. Заморозить baseline и превратить проверки в постоянные release gates.

## Порядок поставки

Работа идёт небольшими проверяемыми пакетами:

1. один подтверждённый дефект или один scorecard-пробел;
2. тест, который воспроизводит проблему;
3. минимальное исправление;
4. целевые проверки, затем полный обязательный набор;
5. production-browser evidence;
6. запись результата и следующего пробела в этом документе.

Формулы и parity выпускаются синхронно с Flutter. UI-пакет не смешивается с
SEO-гипотезой, если у них разные доказательства и период оценки.
