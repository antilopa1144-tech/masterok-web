# Подключение и запуск монетизации

## Проверка на компьютере

1. `npm ci`, затем `npm run dev:monetization`.
2. Открыть http://127.0.0.1:3460. Другой порт в PowerShell: `$env:COMMERCE_DEV_PORT="3462"; npm run dev:monetization`. Сохраняйте один hostname: localhost и 127.0.0.1 имеют разные браузерные проекты. Команда принудительно включает только `local`, отключает внешнюю БД и реальные списания, привязывает сервер к loopback. Она не предназначена для production.
3. Рассчитать материалы → «В проект», дать каждому помещению своё название → открыть проект → «Корзина и пакет». Повторное сохранение той же комнаты в текущем сеансе калькулятора обновляет запись; другое название добавляет помещение. Повторно открытый калькулятор создаёт новую запись: проверьте список проекта.
4. Уточнить закупку. Объединение требует одинаковой явной спецификации и фасовки; название не доказывает совместимость. После ручного количества строка остаётся отдельной. Неизвестный запас не восстанавливается из названия мешка.
5. В кабинете войти как `owner@masterok.test`: локальный код показывается на экране. Это локальный тестовый администратор, не production-аккаунт.
6. Заполнить цены, работы, сведения; сохранить раскладку в проект из существующего инструмента и нажать «Обновить схемы» в комплекте. Проверить предпросмотр, оплатить пакет в симуляторе, скачать PDF и XLSX. Для PRO отдельно оплатить тестовый месяц в кабинете; проверить шаблон работ и сравнение версий.
7. `/upravlenie/monetizatsiya/`: тарифы, переключатели, предложения, отдельные показатели заказов и вознаграждений, возвраты. Все данные этого запуска тестовые. Тестовый возврат снимает соответствующее право; повтор с тем же ключом не создаёт второй возврат.

PGlite хранится в `.commerce-data/local`, каталог игнорируется Git. Остановка — Ctrl+C, данные сохраняются. Реальные ключи не нужны и не должны попадать в скриншоты/логи. Для повторяемых проверок: `npm run test:monetization`; для файлов-примеров: `npx tsx scripts/monetization-document-demo.ts`.

## Режимы

- `off` по умолчанию: бесплатная корзина работает, оплаты нет, платные кнопки не выдают неподключённую функцию за доступную.
- `local`: симулятор собственного платёжного сценария, не проверка Robokassa.
- `sandbox`: отдельная схема PostgreSQL, доставка кодов входа через Resend или SMTP, тестовые пароли Robokassa, `IsTest=1`. По умолчанию продажи выключены до настройки.
- `live`: только после отдельного разрешения владельца, договора и проверки всех условий ниже. Автопродление по умолчанию выключено; оплата месяца сама его не включает.

Шаблон переменных: [`.env.commerce.example`](../../.env.commerce.example). Секреты — только в секрет-хранилище окружения. Sandbox и live используют разные ключи и схемы `commerce_sandbox` / `commerce_live` внутри одной БД Timeweb: тариф 1 ГБ не разрешает создать вторую логическую базу. Переключение режима требует нового деплоя, чтобы пул соединений получил нужный `search_path`; не очищать рабочую схему ради теста. На Timeweb исходящий SMTP заблокирован, поэтому для входа по почте использовать уже имеющийся `RESEND_API_KEY` и `COMMERCE_MAIL_FROM` с подтверждённым в Resend доменом отправителя. Тест отправки на произвольный адрес обязателен: служебный `onboarding@resend.dev` для покупателей не подходит. PostgreSQL и обработка данных должны соответствовать выбранному правовому основанию и требованиям РФ; локальная реализация не подтверждает это за оператора.

На 23.09.2026 в Timeweb запущен PostgreSQL 17 `masterok-commerce-live` (ID 4212531, Москва, сеть приложения `Friendly Horologium`, приватный IP `192.168.0.6`, 496 ₽/мес + 48 ₽/мес за активные ежедневные физические копии). Старый пустой кластер ID 4212527 удалён после проверки нового; в аккаунте остался один кластер. Timeweb API дважды создавал кластеры в новых сетях, игнорируя выбранную; дальнейшие попытки создания через этот API прекратить. До тестового подключения держать публичный режим `off`, затем проверять доставку кода и тестовый платёж только в схеме `commerce_sandbox`. Для live код сам выберет `commerce_live`; не переносить туда тестовые данные и не включать live без остальных проверок.

После применения `COMMERCE_DATABASE_URL` открыть `GET /api/commerce/health`: ответ `200 {"database":"ok"}` подтверждает запрос к PostgreSQL и инициализацию схемы; `503` означает недоступность базы. Ответ не содержит адреса, имени пользователя и ошибок драйвера. Этот маршрут не включает продажи и работает при `MONETIZATION_MODE=off`.

## Robokassa

Отдельный магазин для getmasterok.ru уже создан: «Мастерок строительные калькуляторы», MerchantLogin `getmasterok`, статус «Новый» на 23.09.2026. Он ещё не активирован. В личном кабинете после подготовки доступного тестового HTTPS-стенда:

- Выбрать алгоритм подписи и настроить отдельные тестовые Password1/Password2 для sandbox; `ROBOKASSA_HASH_ALGORITHM` должен совпадать. Не копировать пароли другого магазина и не сохранять их в Git.
- Result URL: `https://getmasterok.ru/api/commerce/payment/result`, метод POST. Подписанное уведомление получает `OK` и номер счёта только после серверной обработки.
- Success/Fail URL: `https://getmasterok.ru/api/commerce/payment/return`, метод GET. Возвращает в кабинет, сам по себе прав не выдаёт.
- Для Result2 закрепить официальный публичный сертификат в `ROBOKASSA_RESULT2_CERTIFICATE`; URL `/api/commerce/payment/result2` добавляется к запросу и подписи. Проверить на конкретном магазине суммы, комиссии и OpKey. Основное подтверждение — подписанный ResultURL; статусы также сверяются через OpStateExt в live.
- Возвратам нужны OpKey и отдельный Password3. Полный возврат отправляется без RefundSum, частичный — с суммой. Неопределённый результат запроса не повторяется автоматически: сначала проверить кабинет провайдера.
- Нужен подтверждённый процесс чеков НПД и их аннулирования/коррекции при возврате. Наличие Receipt в запросе не означает, что чек «Мой налог» уже выдан. Переключатель `COMMERCE_CHECKS_NPD_CONFIRMED` ставится только после реальной проверки.

Официальные спецификации: [оплата](https://docs.robokassa.ru/ru/pay-interface), [уведомления](https://docs.robokassa.ru/ru/notifications-and-redirects), [песочница](https://docs.robokassa.ru/ru/testing-mode), [возвраты](https://docs.robokassa.ru/ru/refund-api), [повторные платежи](https://docs.robokassa.ru/ru/recurring-payments). Публичные описания не заменяют тест на подключённом магазине.

## Публичное включение

Получить от владельца публичные ФИО/ИНН продавца НПД (12 цифр) отдельно: владелец не разрешил брать эти реквизиты из анкеты Robokassa для публикации. Не хранить паспорт, дату рождения и адрес регистрации в проекте. Для поддержки владелец разрешил использовать адрес техподдержки уже созданного магазина Robokassa. Задать версию оферты и согласовать фактические условия оказания услуги, возврата, обработки ПД, отдельное согласие где оно нужно. Проверить доставку OTP, TLS и резервное восстановление БД. Проверить требования уведомления Роскомнадзора, размещения БД в РФ, сроки удаления и обработчиков данных по реальному устройству сервиса.

Только после этого: `legalApproved`, `checkoutEnabled`, `COMMERCE_ALLOW_LIVE_PAYMENTS=true`, `COMMERCE_CHECKS_NPD_CONFIRMED=true`. Значения сами по себе не являются доказательством юридической готовности. `proEnabled` можно включать отдельно. Для автопродления дополнительно нужны одобрение провайдера, `ROBOKASSA_RECURRING_APPROVED=true`, `recurringEnabled` и отдельный непредвыбранный флажок клиента. Электронная отмена доступна в кабинете, дальнейшие заявки на продление не отправляются; уже отправленную провайдеру операцию нужно отдельно сверить.

Планировщик сервера должен раз в несколько минут отправлять `POST /api/commerce/jobs` с `Authorization: Bearer <COMMERCE_JOB_SECRET>` (случайный секрет минимум 24 символа). URL не содержит секрет. Задача сверяет ограниченную пачку платежей/возвратов и обрабатывает разрешённые продления. Нужны мониторинг ошибок и ручная сверка неопределённых операций, не слепые повторы списаний. Истёкшие периоды старше окна 7 дней автоматически не догоняются.

## Предложения и отчёты

Каждое предложение задаётся в админке: официальная ссылка, подходящие калькуляторы, пригодность и ограничения, рекламодатель/ИНН, ERID, договор, дата проверки и срок действия. Без договора и модерации не включать. Внешних товарных API и выдуманных цен/наличия нет. Устаревшее предложение автоматически перестаёт выводиться. За маркировку, отчётность ORD/ЕРИР и применимые рекламные отчисления отвечает реальный процесс оператора.

Клики не равны заказам. Продажи партнёра импортируются отдельно по проверенному отчёту с идентификатором, статусом и комиссией; `paid` означает фактическую выплату, а не одобренную заявку. Не загружать персональные данные покупателей. Тестовые и live-метрики разделены. Валовая выручка минус возвраты не является прибылью.

## ИИ и экономика

Пока PRO с ИИ нельзя купить, бесплатный Михалыч работает на прежних условиях, даже если разовая смета уже продаётся. Только после включения работающего PRO общий бесплатный лимит составит 5 вопросов за календарную неделю с понедельника 00:00 мск. PRO за 399 ₽/месяц включает до 100 запросов к Михалычу и помощнику сметы за календарный месяц, в том числе с фото, в пределах бюджета AI 150 ₽ на аккаунт. Это два предела: при тяжёлых вопросах фактическое число ответов может быть меньше 100; это должно быть ясно до покупки. AI и продажа PRO в live закрыты, пока не заданы проверенные рублёвые цены модели, дата проверки (не старше 31 дня), ключ и лимиты. По [официальной таблице DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/) на 23.09.2026 `deepseek-flash` (V4.1 Flash) поддерживает изображения; пиковые ставки составляют $0.30 за 1 млн входных токенов без cache hit и $1.20 за 1 млн выходных. Это долларовые ставки провайдера, а не подтверждённая себестоимость в рублях конкретного аккаунта. Контекст проекта ограничен, контактные сведения автоматически в него не включаются. Неопределённый ответ провайдера сохраняет резерв расходов, чтобы сбои не сделали запросы безлимитными. До публичного запуска проверить на оплачиваемых тестовых запросах, насколько часто бюджет наступает раньше счётчика, и пересмотреть формулировку или бюджет, если это заметно.

Перед запуском хранить запись: commit/окружение/режим, настройки и их версия, тест провайдера, чек, возврат, письмо входа, восстановление БД, юридические документы и решение владельца. Не сохранять секреты или полные клиентские документы в отчёте о проверке.
