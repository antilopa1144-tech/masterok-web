## Дополнительные находки полного обхода

### B10. P1 — ещё семь планировщиков показывают результат при недопустимой геометрии

Подтверждено в production через ввод нуля и сопоставление поля с результатом:

| Инструмент | Ввод | Что продолжает показываться |
|---|---|---|
| Светильники | Ширина комнаты 0, длина 6000 мм | Подпись 0×6000, площадь 3 м², 12 светильников, схема шириной 500 мм |
| Рейки | Ширина стены 0, высота 2700 мм | Схема 300 мм, 6 реек / 16,2 м, купить 7 заготовок |
| Террасная доска | Длина 0, ширина 3000 мм | Площадь 1,5 м², схема 500×3000, купить 5 досок |
| Тротуарная плитка | Ширина 0, длина 5000 мм | Площадь 1,5 м², схема шириной 300 мм, купить 94 элемента |
| Листы | Ширина стены 0, высота 2700 мм | Площадь 0,81 м², 2 детали, купить 2 листа |
| Обои | Комната 4×5 м, высота 0 | Подпись 4×5×0, площадь 27 м², 36 полос, 7 рулонов: высота внутри ограничена 1,5 м |
| Линейный раскрой | Заготовка длиной 0 мм | Заголовок 0 мм, описание закупки «по 100 мм»; деталей 0. Здесь есть предупреждение о деталях, не помещающихся в заготовку, но сам размер всё равно подменён |

Причина: `src/components/tools/VisualToolPrimitives.tsx` хранит числовое значение через `Number(event.target.value)`; используется в пяти новых планировщиках. У листов и обоев похожие локальные компоненты. Расчётные библиотеки ограничивают числа, а поля/подписи продолжают использовать исходные. Вместе с плиткой, ламинатом и кирпичом проблемный класс охватывает **10 инструментов раскладки/планирования**.

Решение: общий контракт NumericDraft + валидируемый снимок данных. Защитную нормализацию движка сохранить, но она не должна создавать пользователю «другую комнату» без сообщения. При пустом/недопустимом поле — объяснение и отсутствие нового актуального заказа/экспорта. Можно оставить предыдущую схему с явной пометкой «по предыдущим данным».

### B11. P1 — существующий арифметический калькулятор закрыт маршрутным фильтром

Production: каталог инструментов ссылается на `/instrumenty/kalkulyator/`, страница стабильно показывает «Страница не найдена». В исходниках есть `src/app/instrumenty/kalkulyator/page.tsx` и QuickCalculator.

Точная причина: `scripts/generate-route-manifest.ts:39` отбрасывает `TOOL_CONFIGS` с `noindex`. `src/middleware.ts:95–99` использует полученный список как перечень существующих страниц. Так SEO-запрет индексации превращён в запрет доступа. Это не просто забытая регенерация: нынешний генератор воспроизводит дефект.

Решение: список существующих маршрутов строить по всем опубликованным инструментам; noindex применять отдельно только к метаданным/индексации. Перегенерировать manifest из исправленного генератора. Проверка: все ссылки каталога отвечают страницей инструмента, а noindex-инструмент остаётся доступен и сохраняет noindex.

### B12. P1 — повреждённый select в URL делает кнопку расчёта неработающей

Production: `/kalkulyatory/steny/paneli-dlya-sten/?panelType=abc`. На экране выбран обычный ПВХ, но результата нет; нажатие «Рассчитать» ничего не исправляет. В консоли `TypeError: Cannot read properties of undefined (reading 'replace')`.

Причина: `useCalculator.ts:87–93` преобразует параметр в NaN, `calculatorValidation.ts:8–24` проверяет только number/slider, все остальные типы принимает. `engine/wall-panels.ts:161` обращается к отсутствующей подписи. Все 65 definitions имеют дискретные поля, всего 336; это общий пробел проверки, но падение всех 65 не утверждается.

Решение: URL parser знает тип каждого поля; finite для числовых значений, switch только 0/1, select/radio только из актуального resolveFieldOptions. Невалидный явный параметр показывается как ошибка, движок не вызывается. Пропуск параметра означает default, но `abc`, пустота и ноль не смешиваются. Изменить тест, который сейчас разрешает select=99; проверить `abc`, `99`, Infinity, пустой параметр, валидный 0 и зависимые options.

### B13. P1 — светильники → потолок теряет площадь и светильники

Production: план 4000×6000 мм / 12 точек передаёт `area=24&corners=4&fixtures=12&roomWidthMm=4000&roomLengthMm=6000`. Целевая форма открывает 5×4 м, результат **20 м²**, проектных позиций **0**.

Причина: `src/lib/tools/lighting-layout-to-ceiling.ts:41–67` использует прежнюю схему. Текущий ceiling-stretch в режиме inputMode=0 читает length/width; fixtures заменён проектными узлами.

Проверенное локально решение: `inputMode=0&length=6&width=4&lightingNodesEnabled=1&projectLightingNodeCount=12`. Действующая публичная формула с этими параметрами даёт **24 м² и 12 узлов**. Не вычислять автоматически длину профиля, закладные других типов или заказную площадь полотна: этих проектных данных планировщик не предоставляет. Обратный helper также читать по текущей схеме, а не устаревшему fixtures.

### B14. P1 — листы → крепёж переносит только несуществующие поля

Код + запуск публичной формулы: `sheet-layout-to-calc.ts:49–71` для 12 листов передаёт materialType, sheetCount, fastenerStep, withFrameScrews, withDubels. Ни одного из этих полей в нынешнем fastenersDef нет; автозапуска нет, остаётся default **240 крепежей**. В полном браузерном обходе сам калькулятор крепежа работал, эта конкретная цепочка проверена контрактно.

Решение: убрать обещание автоматического расчёта крепежа по листам. Оставить переход с понятным требованием ввести проектное количество, подтверждённую норму или линии/шаг. **Нельзя заменить sheetCount произвольным множителем**. Позже полноценный перенос возможен только с данными о системе крепления. Переписать тест старых ключей на вызов целевой схемы и запрет выдуманного количества.

### B15. P1 — два перехода к грунтовке подменяют площадь на 50 м²

Шпаклёвка 24 м² → грунтовка открывает поле **50 м²**, после расчёта результат 50 м². Production подтверждён. Перегородка 5×2,7 м (две стороны =27 м²) воспроизводит ту же ошибку в публичной функции.

Причина: `finishing-stage-links.ts:42–54` и `partition-finishing-links.ts:19–30,59–75` отправляют удалённые area/surfaceType/primerType. При этом тест целевой грунтовки уже фиксирует удаление этих полей, а тесты ссылок продолжают утверждать старые параметры.

Проверенное решение для обеих ссылок: `inputMode=0&projectAreaM2=<площадь>`. Публичная формула принимает ровно **24 и 27 м²**. Старые типы поверхности/продукта не переводить по совпадению чисел: их семантика изменилась, выбор продукта остаётся явным.

### B16. P2 — общий перенос между рекомендованными калькуляторами не знает схемы назначения

Статический и runtime-аудит 265 рёбер CALCULATOR_COMPANIONS: **90** передают хотя бы один неизвестный целевому калькулятору ключ; **70** не передают ни одного распознаваемого числового ключа. Эти группы пересекаются, складывать их нельзя. Пример laminat → linoleum передаёт area/length/width вместо roomLength/roomWidth. Во всех общих переходах на грунтовку действует аналогичная проблема.

Причина: `CompanionLinks.tsx:9–20` и дубликат в `CalculatorWidget.tsx:384–397` слепо копируют area/length/width/height/inputMode. inputMode=1 имеет разный смысл в разных калькуляторах. Приоритет ниже специальных переходов: карточка называется «Также может пригодиться», а не гарантирует перенос расчёта.

Решение: для обычных рекомендаций передавать только from; для переноса — именованный типизированный adapter с проверкой физического смысла и единиц. Устранить дублирование сборщика ссылок. Проверять все рёбра по реестру автоматически.

### B17. P2 — линолеум сообщает нулевое количество шагов закупки

Код + публичная функция: при комнате 5×4 м, рулоне 3 м, направлении вдоль длины и припуске 10 см точная потребность 10,2 пог. м. При шаге 0,1 м закупка 10,2 м, но `buy_plan.packages_count=0` вместо 102 шагов; при шаге 0,5 м закупка 10,5 м, остаток 0,3 м, count снова 0 вместо 21. Сам общий метраж закупки в этих примерах правильный. Общий блок результата из-за count=0 скрывает расшифровку шага.

Причина: `formulas/linoleum.ts:247–265` явно записывает 0, canonical считает число шагов. Из defaults всех 65 это единственный результат с положительной закупкой и фасовкой, но нулевым count.

Проверенное решение: `Math.round(purchaseLinearM / purchaseStepM)` после округления закупки. UI называет это **шагами продажи**, а не физическими упаковками или рулонами. Тесты на 0,1 / 0,5 / 1 м; равенство количества шагов × шаг = метраж в допустимой погрешности.

### B18. P2 — оценка стоимости показывает дробные двери и мешки как позиции сметы

Production, стандартный ремонт 55 м²: 19,3 мешка штукатурки, 2,8 мешка клея, **2,2 двери**. Цена двери 10 000 ₽ даёт строку 22 000 ₽ и диапазон 18 700–25 300 ₽. `renovation-cost.ts:155` округляет все единицы до десятых независимо от штучности. Сервис честно называет итог приблизительным и предлагает точную закупку отдельно, поэтому это не доказательство неправильной полной сметы, но представление штучных позиций вводит в заблуждение и не соответствует правилам проекта.

Решение: отличать предварительную удельную потребность от закупки. Для штучных позиций показывать целое покупаемое количество с возможностью явного ввода; цену закупки умножать на него. Для мешков иметь фасовку и точную массу отдельно. Не выдавать 2,2 двери как готовую позицию к покупке; не подменять пользовательский проект автоматически тремя дверями без пояснения о приблизительной модели. Обновить тест, сейчас закрепляющий 19,3 мешка.

### B19. P2 — календарь показывает несовместимые сроки одного сценария

Production: паспорт ванной пишет «2–4 недели», расписание заканчивается на **48-й день**. Это арифметическое противоречие интерфейса, независимо от того, какие сроки технологически подходят конкретным смесям. `src/lib/renovation-calendar/scenarios.ts:42` / данные сценариев следует связать с показанными диапазонами, а не поддерживать две независимые оценки.

Решение: общий диапазон выводить из конечных этапов выбранного плана, явно указывая ориентировочность. Нормы, технологическую очередность и сроки материалов проверять отдельно по проекту и инструкциям. В частности, категоричные утверждения текста о единственно возможном положении гидроизоляции не считать подтверждёнными этим UI-аудитом.

## Дополнительные замечания, не выдаваемые за live-критические баги

- QuickCalculator `toggleSign` в `src/components/tools/QuickCalculator.tsx:125` меняет знак начала всего выражения: строка `5+2` становится `-5+2`. `percent` использует parseFloat всей строки. После восстановления маршрута отдельно определить семантику +/- и % текущего операнда и закрепить сценариями; сейчас выполнение этих кнопок на production заблокировано B11. Не заявляется как воспроизведённое браузером.
- В чек-листах справочный ответ предлагает печать/PDF, хотя появился рабочий локальный прогресс. В сравнении материалов нижняя справка говорит о рыночных ценах, хотя цены сейчас вводит пользователь. Исправить устаревшую справку вместе с текущими контрактами.
- «Площадь комнаты», все шесть форм: расчёты переключаются, но паспорт одинаково пишет A×B даже для радиуса/угла сектора. Это нуждается в понятных подписях по форме. В непрямоугольной комнате «Собрать материалы» открывает мастер без переноса геометрии; не обещать перенос там, где модель мастера не поддерживает форму.
- Потенциальная гонка асинхронного расчёта мастера из первого отчёта остаётся code-risk, отдельное воспроизведение не получено. Включить её в защиту версией расчёта.

## Почему это произошло

1. **Число подменило редактируемый текст.** Значение `2`, пустая строка и законченные `20` — разные этапы редактирования, но компоненты нормализуют их как готовый расчёт. Защитный clamp движка стал незаметной правкой пользовательского проекта.
2. **Обновлялись целевые схемы, но не все отправители.** Примеры потолка и грунтовки показывают конкретный механизм: старые ключи остаются в helpers, целевой hook игнорирует их и использует defaults. Тесты отправителя и получателя по отдельности зелёные и противоречат друг другу.
3. **Сходство названий приняли за единый контракт.** Общий блок переносит inputMode и размеры без понимания единиц/смысла назначения.
4. **Результат не привязан к версии формы.** Reset очищает видимую форму, а уже поставленный debounce может вернуть старые данные.
5. **Смешаны доступность и индексация.** noindex ошибочно исключает маршрут из существующих.
6. **Проверка ядра не охватывала публичную цепочку.** `tests/parity.test.ts:41–118` вызывает canonical engine, а не `registry/getCalculateFn` и UI adapters. 41 из 65 definitions непосредственно вызывает canonical engine; 19 имеют собственный web-расчёт при импорте canonical config, ещё 5 специализированы. **24/65 не означают 24 неверные формулы**, но текущий parity не доказывает их совпадение с mobile. 3522 зелёных теста также не сертифицируют браузерный ввод и реальные переходы.

Независимые web-формулы в группе 19: attic, ceiling-cassette, ceiling-rail, ceiling-stretch, drainage, fasteners, fence, linoleum, parquet, paving-tiles, primer, putty, self-leveling, siding, sound-insulation, terrace, wallpaper, waterproofing, windows. Специализированные 5: balcony, bathroom, doors, lawn, slopes.

## Конкретный план исправлений и защиты от повторения

### Пакет 1 — восстановить ввод и согласованность результата

### Проверка контракта переходов

Проверены специализированные builders: tile→tile/adhesive/grout; laminate; room-area→laminate/tile/wallpaper; wallpaper; brickwork; paver; deck; sheet→drywall-wall/drywall-ceiling/fasteners; lighting→ceiling. Проверены continuation helpers foundation/concrete, screed/electric-floor, finishing, partition-finishing, roof, facade. Совпадение ключей у остальных builders не заменяет браузерную проверку всех их режимов.

В `contract-probes.ts` отдельно закреплены воспроизведения B11–B15, B17 и проверенные без изменения приложения новые параметры для B13/B15 и количества шагов B17. Скрипт подтверждает наличие нынешних дефектов; это исследовательский артефакт, а не зелёная регрессия исправленной версии.
