# Раскладка ламината: production canonical и поисковые варианты

Проверка 10 сентября 2026 через HTTP с российского VPS, Google URL Inspection и свежий список Яндекс in-search. Приватный ответ: `.local-analytics/laminate-canonical-2026-09-10.json`.

## Подтверждено

- Основной URL и пять проверенных вариантов с параметрами возвращают HTTP 200 без редиректа. В каждом HTML ровно один canonical: `https://getmasterok.ru/instrumenty/raskladka-laminata/`. Robots разрешает индексацию; конкурирующего canonical в HTML нет.
- Google: основной URL проиндексирован, выбранный Google canonical совпадает с основным URL; последний обход 4 сентября. Исходный подозрительный вариант `surfaceW=19500&surfaceH=3170&mode=herringbone` неизвестен Google. Это не проверка всех параметрических URL Google.
- Яндекс: исходный подозрительный вариант отсутствует в текущей полной выгрузке in-search, но четыре других варианта присутствуют. Поэтому исторические показы не доказывают текущий статус исходного URL, а наличие правильного canonical не доказывает склейку всех вариантов Яндексом.

Текущие варианты Яндекса (после `/instrumenty/raskladka-laminata/`):

| Параметры | HTTP | HTML canonical |
|---|---|---|
| `?surfaceW=1170&surfaceH=1710&mode=deck-third` | 200 | Основной URL |
| `?surfaceW=10000&surfaceH=1220&mode=herringbone` | 200 | Основной URL |
| `?surfaceW=3600&surfaceH=5000&mode=deck-half&verify=f3cce13` | 200 | Основной URL |
| `?surfaceW=3600&surfaceH=5000&mode=deck-half&deploy=f3cce13` | 200 | Основной URL |

## Решение и граница завершения

Дефекта формирования canonical не найдено: цепочка `page.tsx → buildToolPageMetadata → buildPageMetadata` задаёт постоянный основной URL, production подтверждает результат. Повторно добавлять canonical, вводить общий noindex или удалять параметры редиректом не нужно.

Параметры `surfaceW`, `surfaceH`, `mode` читаются клиентом через `parseLaminateLayoutSearchParams` и меняют расчёт. Они не просто рекламные метки; удаление их из пользовательского URL теряет выбранную комнату. `verify` и `deploy` в этом парсере не используются. Для будущих production QA не добавлять произвольные индексируемые query-метки.

Отдельный остаток — консолидация вариантов Яндексом. По [официальной инструкции Clean-param](https://yandex.ru/support/webmaster/ru/robot-workings/clean-param) правило предназначено для незначащих параметров; оно не требует Disallow. Возможное следующее техническое изменение — узкое правило для `verify`/`deploy` в пределах маршрута. Расчётные параметры требуют отдельного решения о поисковой политике: они меняют результат, поэтому не объявлять их незначащими автоматически. Изменения robots и настроек кабинета в этой проверке не выполнялись.

Не подтверждены: выбранный canonical каждого варианта Яндексом, вред для ранжирования, динамика консолидации, пользовательский browser-flow всех ссылок. HTTP-проверка не заменяет UI-тест. Нет оснований задерживать редакционную работу или обещать рост от технической переделки.

Следующий контентный этап: проверить самостоятельный спрос на направление укладки, переходы между комнатами и подрезку последнего ряда; не дублировать уже опубликованную статью о смещении.
