# Project Workflow

## Начать безопасно

1. Прочитать корневой `AGENTS.md`.
2. Проверить `git status --short` и отделить чужие изменения.
3. Сформулировать границы, источник истины, пользовательский эффект и критерии готовности.
4. Найти только нужные entry points через `rg --files`, `rg` и точечное чтение.

## Подключить нужный workflow

- Новый или изменяемый калькулятор: `$build-calculator`.
- Проверка корректности без автоматической правки: `$audit-calculator`.
- Фактический UI-сценарий: `$verify-user-flow`.
- SEO/GEO/AEO-аудит: `$audit-seo-evidence`.
- Production-инцидент: `$diagnose-production`.
- Финальные проверки, commit и push: `$ship-masterok`.
- Параллельные независимые части: `$delegate-efficiently`.
- Узкая формула или упаковка: `calc-core`, `construction-domain`, `testing-validation` по необходимости.

Использовать минимальный набор скиллов, покрывающий задачу. Не загружать пересекающиеся навыки без отдельной пользы.

## Использовать SocratiCode осознанно

Для рефакторинга, переименования общего модуля или неясного execution flow сначала проверить доступность SocratiCode. При готовом индексе использовать symbol, flow и impact для blast radius. Не строить индекс ради простой локальной правки. Если Docker, индекс или граф недоступны, продолжить через `rg`, imports, тесты и существующую карту проекта, явно указав ограничение.

## Делегировать экономно

По умолчанию работать одним агентом. Подключать `$delegate-efficiently` только при двух и более независимых ветках, когда параллельность заметно улучшит скорость или даст важную независимую проверку. Не создавать субагента лишь потому, что задача выглядит большой.

## Выполнить изменение

1. Разбить работу на проверяемые этапы.
2. Начать с regression-теста для принесённого бага.
3. Делать минимальные task-owned diff без скрытого рефакторинга.
4. После каждого смыслового этапа запускать самую узкую релевантную проверку.
5. Перед завершением выполнить проверки по риску и перечитать итоговый diff.

## Завершить

Сообщить результат, файлы, проверки, незакрытые риски и ручные шаги. Не смешивать source evidence, test evidence, browser evidence и production evidence.
